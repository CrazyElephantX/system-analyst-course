# Acceptance Criteria Template (Gherkin)

Этот шаблон помогает формализовать критерии приемки к пользовательским требованиям и сразу превращать их в тестируемые сценарии в формате Given–When–Then.

---

## 1. Структура шаблона

Используйте таблицу следующего вида (в Markdown, Excel, Google Sheets, Confluence — формат колонок одинаковый):

| AC Code       | Story Key   | Feature / Epic | Business Priority | Acceptance Criteria (short)                                        | Given                                                                                     | When                                                              | Then                                                                                         | And / But (optional)                                                        | Notes (BA)                                  | Notes (QA / Dev)         |
| ------------- | ----------- | -------------- | ----------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------- | ------------------------ |
| AC-<STORY>-1  | PROJECT-123 | Календарь      | Must              | Пользователь видит события календаря текущего дня                  | Пользователь авторизован и открыл экран календаря на текущую дату                         | Система успешно загрузила события за выбранную дату              | Пользователь видит список событий только за текущий день                      | And события отсортированы по времени начала                                   | Пример happy‑path сценария                |                            |
| AC-<STORY>-2  | PROJECT-123 | Календарь      | Should            | Пользователь видит ошибку загрузки событий текущего дня            | Пользователь авторизован и открыл экран календаря на текущую дату                         | Сервис событий недоступен или вернул ошибку                     | Пользователь видит сообщение об ошибке загрузки событий                       | But список событий не отображается                                           | Пример обработки ошибки                   |                            |
| AC-<STORY>-3  | PROJECT-123 | Календарь      | Could             | Пользователь не видит событий, если на день ничего не запланировано | Пользователь авторизован и открыл экран календаря на текущую дату                         | В календаре нет событий на выбранную дату                      | Пользователь видит пустое состояние без списка событий                        | And пользователь видит текст о том, что на этот день событий нет             | Пример граничного кейса (пустой день)     |                            |

## 2. Описание полей

- **AC Code**  
  Уникальный код критерия вида `AC-<код Story>-<порядковый номер>` (например, `AC-CAL-123-1`).  
  Используется для трассировки: ссылки в постановках задач, тест‑кейсов и баг‑репортах.

- **Story Key**  
  Ключ User Story / задачи в Jira, YouTrack и других трекерах (например, `CAL-123`).  

- **Feature / Epic**  
  Название функционального блока или эпика, к которому относится история (например, «Календарь»).  

- **Business Priority**  
  Приоритет критерия для бизнеса — можно использовать схему Must / Should / Could / Won’t или свою шкалу.

- **Acceptance Criteria (short)**  
  Краткая формулировка критерия на бизнес‑языке: что должно быть **правдой**, чтобы история считалась выполненной.

- **Given**  
  Предварительные условия и контекст: роль пользователя, состояние данных, режим работы системы (например, «Пользователь авторизован и открыл экран календаря на текущую дату»).

- **When**  
  Действие пользователя или событие в системе, которое запускает сценарий (например, «Система успешно загрузила события за выбранную дату»).

- **Then**  
  Ожидаемый результат, который можно проверить: что видит пользователь, какие данные показываются, какое поведение проявляет система.

- **And / But (optional)**  
  Дополнительные проверки и негативные условия:  
  - `And` — то, что тоже должно быть истинно (например, сортировка, фильтры, формат данных).  
  - `But` — то, чего быть не должно (например, «But список событий не отображается» в случае ошибки).

- **Notes (BA)**  
  Комментарии системного / бизнес‑аналитика: уточнения бизнес‑правил, ограничения, ссылки на решения, протоколы встреч.

- **Notes (QA / Dev)**  
  Комментарии от тестирования и разработки: решения по реализации, технические ограничения, особенности автотестов.

## 3. Как использовать шаблон шаг за шагом

1. **Выберите User Story**  
   Определите историю, для которой будете описывать критерии приемки.

2. **Сформируйте список бизнес‑критериев**  
   Сформулируйте отдельные бизнес‑утверждения вида «Пользователь может… / Пользователь видит… / Система должна…», каждое — один будущий критерий.

3. **Заведите строки в таблице**  
   Для каждого критерия:
   - Заполните `Story Key` и `Feature / Epic`.  
   - Присвойте уникальный `AC Code` по шаблону `AC-<Story>-<номер>`.  
   - Запишите краткий текст в `Acceptance Criteria (short)`.

4. **Разложите критерий на Gherkin‑шаги**  
   Для каждой строки заполните:
   - `Given` — кто и в каком контексте, какие данные и настройки уже есть.  
   - `When` — что происходит, какое действие или событие запускает логику.  
   - `Then` — какой результат должен быть виден или зафиксирован.  
   - `And / But` — дополнительные условия, позитивные и негативные, при необходимости.

5. **Проведите совместный просмотр с бизнесом и командой**  
   Пройдитесь по таблице вместе с бизнес‑представителями, разработкой и тестированием:
   - Уточните формулировки так, чтобы они были понятны всем участникам.  
   - Обсудите корнер‑кейсы: ошибки, пустые состояния, особенности по ролям и правам доступа — добавьте их отдельными строками в таблицу.
   - Зафиксируйте договоренности в `Notes (BA)` и `Notes (QA / Dev)`.

6. **Свяжите шаблон с постановкой задач**  
   Добавьте ссылку на этот файл (или его копию) в постановку задачи на разработку / спецификацию реализации, чтобы цепочка «пользовательские требования → критерии приемки → реализация → тестирование» была прозрачной.

---

## 4. Рекомендации по практическому применению

- Храните шаблон в общем репозитории (Git) или в корпоративном Wiki и используйте как стандартный артефакт при работе с пользовательскими требованиями.
- Используйте `AC Code` для связи с тест‑кейсам и дефектами: это сильно упрощает анализ покрытия и разбор инцидентов.  
- Обновляйте строки при изменении требований, чтобы сохранить актуальную точку правды для команды.  
- На воркшопах и рабочих сессиях выводите эту таблицу на экран и заполняйте совместно — это помогает находить скрытые сценарии и разночтения еще до разработки.
